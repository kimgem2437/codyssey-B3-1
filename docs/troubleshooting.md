## 1. IAM 사용자 콘솔 로그인 실패

| 항목 | 내용 |
|---|---|
| 증상 | IAM 사용자 로그인 화면에서 `Authentication failed - 인증 정보가 정확하지 않습니다` 반복 발생 |
| 원인 가설 | ① 계정 ID 칸에 폐쇄된 이전 계정의 별칭이 남아 있어 다른 계정으로 로그인 시도 ② IAM 사용자 비밀번호 대신 루트 비밀번호 입력 ③ 비밀번호 입력 오류(한/영 전환, 자동 생성 암호 미확인) |
| 검증 방법 | 루트로 로그인해 IAM 콘솔에서 확인: `b3-1-user` 존재, 암호 수명 표시(콘솔 액세스 활성화), 정책 `연결된 엔터티`에 사용자 연결 확인 → 사용자·권한 설정은 정상. 정책 ARN에서 새 계정 ID(12자리)를 확인해 계정 ID 칸을 수정 → 같은 오류 지속 → 비밀번호가 원인으로 좁혀짐 |
| 조치 내용 | ① 계정 ID 칸을 새 계정 ID(12자리)로 수정 ② 루트에서 `보안 자격 증명 → 콘솔 액세스 관리 → 암호 재설정(사용자 지정 암호)` ③ 메모장에 쓴 비밀번호를 붙여넣고 Show Password로 일치 확인 |
| 결과 | `b3-1-user`로 콘솔 로그인 성공 (오른쪽 위 `b3-1-user` 표시) |
| 재발 방지 | 사용자 생성 직후 **콘솔 로그인 URL**(계정 ID 포함)을 저장해 두고 그 URL로만 접속. 루트와 IAM 사용자 비밀번호는 비밀번호 관리자에 구분해서 저장 |

### 배운 점

- 루트 사용자와 IAM 사용자는 **서로 다른 자격 증명**이다. 같은 계정이어도 비밀번호를 공유하지 않는다.
- IAM 로그인은 **계정 ID + 사용자 이름 + 비밀번호** 세 가지가 모두 맞아야 한다. 계정 ID가 틀리면 사용자가 있어도 찾을 수 없다.
- 권한(정책)은 로그인 **이후**에 적용된다. 로그인 실패는 권한 문제가 아니라 인증 문제다.

## 2. 외부에서 /health 접속 타임아웃

> 보안 그룹의 역할을 검증하기 위해 `b3-1-web-sg` 인바운드에서 HTTP(80) 규칙을 삭제해 의도적으로 재현했다.

| 항목 | 내용 |
|---|---|
| 증상 | 노트북에서 `GET http://43.201.85.164/health` 요청 시 `curl: (28) Connection timed out after 10000 milliseconds`. 직전까지 200 OK였던 요청이 응답 자체를 받지 못함 |
| 원인 가설 | A. EC2가 꺼짐 / B. 라우팅·IGW 문제 / C. Nginx 중지 또는 80 미수신 / D. Security Group이 80 인바운드를 차단 |
| 검증 방법 | 아래 4단계로 가설을 하나씩 제거 |
| 조치 내용 | `b3-1-web-sg` 인바운드에 **HTTP / TCP 80 / 0.0.0.0/0** 규칙 재추가 |
| 결과 | 80 포트 `TcpTestSucceeded : True`, `/health` → `HTTP/1.1 200 OK` / `OK`. Nginx 접속 로그에 노트북 공인 IP 요청 기록 확인 |
| 재발 방지 | 보안 그룹 수정 후 반드시 **외부에서** `/health` 호출로 확인. 배포 체크리스트에 "SG 인바운드: 80=0.0.0.0/0, 22=내 IP/32" 항목 추가. 서버 내부 curl 성공만으로 "정상"이라 판단하지 않기 |

### 검증 과정

| 단계 | 확인 내용 | 결과 | 결론 |
|---|---|---|---|
| ① 포트별 연결 테스트 (노트북) | `Test-NetConnection` 80 / 22 | 80: **False**, 22: **True** | 같은 서버에 22는 도달 → EC2 실행 중, 라우팅·IGW 정상. **가설 A, B 제거** |
| ② 서버 내부 상태 (SSH) | `systemctl is-active nginx`, `ss -tlnp` | `active`, `0.0.0.0:80`·`[::]:80` LISTEN (nginx) | Nginx가 모든 주소의 80을 수신 중 |
| ③ 서버 내부 요청 | `curl -i http://localhost/health` | `200 OK` / `OK` | 애플리케이션 정상. **가설 C 제거** |
| ④ 접속 로그 | `/var/log/nginx/access.log` | 차단 시간대(04:41~04:47 UTC)에는 `::1`(localhost) 요청만 있고 **외부 요청 기록 없음** | 요청이 **서버에 도달하기 전에** 차단됨 → 인스턴스 앞단 방화벽 |
| ⑤ 콘솔 확인 | `b3-1-web-sg` 인바운드 규칙 | SSH 22만 존재, **HTTP 80 없음** | **가설 D 확정** |

### 핵심 근거: 접속 로그

- 차단 전 04:40:07 — 노트북 IP의 `GET /health 200` 기록 있음
- 차단 중 04:45:54 — `::1`(서버 내부) 요청만 기록, 같은 시간대 노트북에서 보낸 요청은 **기록 없음**
- 복구 후 04:47:33 — 노트북 IP의 `GET /health 200` 기록 다시 나타남

Nginx 로그에 요청이 남지 않았다는 것은 Nginx가 요청을 거부한 것이 아니라 **요청을 받지조차 못했다**는 뜻이다. 서버 프로세스·라우팅이 정상인 상태에서 패킷이 인스턴스에 닿기 전에 버려졌으므로, 인스턴스 네트워크 인터페이스 단에서 동작하는 **Security Group**이 원인이다.

### 추가로 관찰한 것

접속 로그 맨 위에 `59.182.1.230 ... "GET /boaform/admin/login.asp" 404` 요청이 있다. 80 포트를 연 지 **몇 분 만에** 모르는 IP가 관리자 로그인 페이지를 찾는 자동 스캔을 보냈다. 인터넷에 공개된 포트는 즉시 스캔 대상이 된다는 뜻이며, SSH(22)를 0.0.0.0/0이 아닌 **내 IP/32로 제한**한 이유를 보여주는 실제 사례다.

### 배운 점

- 타임아웃(응답 없음)과 거부/에러 응답은 다르다. **타임아웃은 방화벽이 패킷을 조용히 버릴 때** 주로 나타난다.
- 원인은 **바깥에서 안쪽으로** 좁힌다: 포트 도달 여부 → 서버 프로세스 → 서버 내부 요청 → 로그 → 설정.
- Security Group은 **기본 거부**(허용 규칙이 없으면 차단)이고, 규칙 변경은 인스턴스 재시작 없이 즉시 반영된다.
